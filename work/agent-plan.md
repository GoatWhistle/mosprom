# Brim: агент в Compose и встроенный чат STE Slicer

## 1. Результат и архитектура

Создать систему, в которой пользователь общается с агентом внутри STE Slicer, агент принимает решения на backend, а плагин исполняет его инструменты через API слайсера.

Размещение:

| Компонент | Стек и ответственность |
|---|---|
| backend в Compose | Python 3.12, FastAPI, собственный цикл агента, OpenAI-совместимый LLM-адаптер |
| db в Compose | PostgreSQL 16: история, требования, действия, подтверждения, вложения и результаты |
| migrate в Compose | Одноразовый сервис dbmate для SQL-миграций |
| Плагин STE Slicer | Python 3.5-совместимый код, PyQt5 и QML: встроенный чат, состояние сцены, исполнение инструментов |
| Движок STE Slicer | Слайсинг, генерация G-code, сохранение проекта 3MF |

Плагин подключается к настраиваемому адресу backend; по умолчанию — http://localhost:8000. Compose может работать на другой машине.

Использовать существующую структуру backend/src/app/: domain, usecase, repository, adapter, controller. Сценарии и порты не зависят от FastAPI, PostgreSQL, LLM-провайдера или Qt. Зависимости собираются в composition root.

Плагин разместить в plugin/Brim/, также разделив протокол, сценарии исполнения, интеграцию со слайсером и UI. Современные зависимости backend внутрь слайсера не переносить.

Отдельный веб-фронтенд, управление парком принтеров, веб-поиск, RAG и собственный генератор G-code в реализацию не входят.

## 2. Backend, протокол и хранение

Цикл агента

Заменить шаблонный интерфейс одиночного структурированного ответа интерфейсом диалога: сообщения, изображения, определения инструментов, вызовы инструментов и их результаты. Реализовать OpenAICompatibleChatAdapter через существующий HTTP-клиент httpx.

Адаптер только преобразует запросы и ответы Chat Completions. Исполнение инструментов, подтверждения и продолжение диалога принадлежат use cases. Не использовать Claude Agent SDK, Codex SDK и отдельную decision-модель для принятия решений по печати; убрать их неиспользуемую конфигурацию и зависимости при замене шаблона.

Состояния выполнения: сбор требований, работа агента, ожидание пользователя, ожидание подтверждения, исполнение инструмента, слайсинг, сохранение, завершение, ошибка и прерывание. Переходы сохранять в БД.

Связь с плагином

- HTTP API под /api/v1: диалоги, сообщения, вложения, режим работы, подтверждения, остановка запуска и скачивание артефактов.
- Исходящее WebSocket-соединение плагина с backend: регистрация экземпляра слайсера, снимки состояния, события чата, команды инструментов, результаты и прогресс.
- Каждая команда содержит идентификатор вызова, идентификатор запуска и ожидаемую версию состояния. Результат содержит фактическое состояние, ошибки и сведения о выполненных изменениях.
- Плагин реализует минимальный MCP-диспетчер: initialize, tools/list, tools/call. Один диспетчер обслуживает локальный HTTP MCP endpoint и сообщения, переданные через соединение с backend. WebSocket служит мостом доставки; его не выдавать за стандартный HTTP-транспорт MCP.
- Определения инструментов имеют один источник; из него формируются MCP-каталог и описания tools для LLM. Версии контрактов проверяются при подключении.
- Подключение защищается токеном экземпляра. Для удалённого адреса использовать HTTPS/WSS; локальный адрес допускает HTTP/WS. PostgreSQL наружу не публиковать.

Запустить backend одним процессом на первом этапе. Выполнение организовать фоновыми задачами приложения с сохранённым состоянием в PostgreSQL, без Redis и отдельной очереди.

Надёжность исполнения

На один экземпляр слайсера разрешён один активный запуск, меняющий сцену. Повторная доставка известного вызова возвращает сохранённый результат, а не повторяет изменение.

После разрыва связи выполнение приостанавливается. При переподключении стороны сверяют незавершённые вызовы и актуальное состояние. Неопределённый исход изменения не считать ни успехом, ни поводом слепо повторить операцию.

Ручное изменение сцены увеличивает её версию. Устаревший пакет изменений возвращается агенту для пересмотра. Внешние вызовы и ожидание пользователя выполняются вне открытых транзакций БД.

Хранение

Использовать psycopg 3, psycopg_pool, параметризованный SQL и Unit of Work; без ORM. Миграции — в backend/migrations/postgres/.

Хранить:

- диалоги, сообщения и собранные требования;
- экземпляры слайсера и версии снимков состояния;
- запуски агента, вызовы инструментов, события и ошибки;
- пакеты изменений и решения пользователя;
- задания слайсинга, расчётные показатели;
- вложения, G-code, 3MF и дополнительные изображения.

Бинарное содержимое также хранить в PostgreSQL, с именем, типом, размером и контрольной суммой. Для передачи крупных файлов использовать части; временные файлы плагина считать восстанавливаемым кэшем. Постоянное хранение не должно зависеть от файловой системы контейнера.

LLM URL, модель и ключ вводятся через настройки плагина. Ключ хранится в настройках приложения и передаётся backend для работы активного подключения; не записывать его в историю, журналы и результаты инструментов.

## 3. Поведение агента и инструменты

Опрос

Агент формирует начальный список вопросов по конкретной задаче. Пользователь отвечает свободным текстом. Агент уточняет пропущенное и неоднозначное; уже сообщённое повторно не спрашивает.

До достаточного понимания задачи разрешены чтение и анализ. Агент не заполняет существенные пробелы предположениями. При ответе «не знаю» объясняет варианты и помогает пользователю определиться.

Требования, решения и объяснения формирует LLM. Код не выбирает материал, ориентацию или параметры по зашитым правилам.

Автоматический контекст

Без инструментальных запросов со стороны LLM передавать:

- активный принтер, возможности, доступные режимы и экструдеры;
- выбранные материалы, профиль и пользовательские переопределения;
- краткие каталоги совместимых профилей и материалов;
- вложения диалога;
- объекты сцены, их ID, трансформации и базовые численные характеристики;
- состояние расчёта, ошибки слайсера и изменения после последнего действия.

Полный справочник настроек и подробные описания не помещать в каждый запрос: для них предоставить инструменты чтения.

Инструменты LLM

| Инструмент | Контракт |
|---|---|
| apply_changes | Упорядоченный пакет конкретных операций, выбранных агентом |
| search_settings | Поиск доступных параметров с типами, единицами, ограничениями и текущими значениями |
| inspect_profile | Подробные значения выбранного профиля |
| inspect_material | Факты из описания материала в слайсере |
| analyze_geometry | Численный анализ выбранных объектов |
| render_scene | Дополнительное изображение с выбранного ракурса |
| slice | Расчёт текущего состояния и автоматическое сохранение G-code и 3MF |
| ask_user | Список вопросов или уточнение; перевод запуска в ожидание ответа |

apply_changes поддерживает закрытый перечень операций:

- выбор режима, профиля и материала;
- изменение глобальных настроек и настроек экструдера;
- сброс выбранных переопределений;
- импорт модели или открытие 3MF;
- перемещение, поворот и масштабирование;
- создание копий, автоматическую расстановку и удаление;
- создание и сохранение пользовательского профиля.

Для трансформаций использовать абсолютные значения, явно задавать единицы, систему координат и центр вращения. Для открытия 3MF различать восстановление проекта и импорт геометрии.

Пакет — единица подтверждения, но не обещание транзакционности API слайсера. Перед исполнением проверить известные условия; при ошибке остановить пакет и вернуть перечень уже выполненных операций и текущее состояние.

Режимы

- Auto: после опроса агент самостоятельно применяет изменения и запускает расчёт.
- Ask before edits: пользователь видит конкретный пакет изменений и объяснение, затем принимает, отклоняет или уточняет его.

Разрешение проверяется кодом непосредственно перед исполнением. Оно привязано к содержимому пакета и версии сцены. После ручного изменения сцены прежнее подтверждение нельзя использовать автоматически.

Слайсинг подтверждённой конфигурации и сохранение результата дополнительного подтверждения не требуют. Переключение режима влияет на ещё не начатые действия и не отменяет выполненные.

Завершение и ошибки

После первого успешного расчёта и сохранения обоих файлов агент выдаёт результат и останавливается. Автоматическое улучшение результата не запускается.

При ошибке агент может исправлять настройки в рамках требований и текущего режима. Начальный предел — три последовательные неудачные попытки исправления одной операции; после этого агент сообщает причину и запрашивает помощь. Предел вынести в конфигурацию.

Новый запрос пользователя продолжает работу с проектом. Если активная сцена принадлежит другой задаче, явно предложить восстановить сохранённый 3MF; историю диалога не считать доказательством текущего состояния слайсера.

## 4. Плагин, геометрия и результаты

Встроенный интерфейс

Создать немодальное окно чата внутри приложения на PyQt5/QML, открываемое из меню Brim. Использовать штатный QML-механизм слайсера, без браузера и WebView. Такой механизм присутствует в публичном плагине STE Slicer (https://github.com/stereotech/STE-Slicer/blob/develop/plugins/MachineSettingsAction/MachineSettingsAction.py); соответствие выданной версии проверить до разработки основного UI.

Окно включает историю диалогов, сообщения, прикрепление файлов, переключатель режима, карточки подтверждений, видимые действия инструментов, прогресс, ошибки и скачивание результатов. RU по умолчанию, EN через словари.

Прикрепление файла только сохраняет его в диалоге. Загрузка в сцену происходит по инструменту агента. Поддержать JPG/PNG, STL/OBJ/3MF; текст задания пользователь может отправить сообщением.

Исполнение в STE Slicer

Сетевую работу выполнять вне главного потока. Доступ к сцене, настройкам, запуску расчёта и созданию снимков для анализа — через главный поток Qt.

На время применения пакета управлять штатным автослайсингом, чтобы изменения не запускали промежуточные расчёты. После завершения или ошибки восстанавливать предыдущее поведение.

Поддержать classic, cylindrical, cylindrical_full и основной профиль Stereotech Hybrid 530 V5.2.4. Реальные идентификаторы и API извлечь из выданного дистрибутива, не выводить из предположений.

Геометрия

Базовые сведения поступают автоматически: габариты, границы в координатах сцены, трансформации и число треугольников.

Подробный анализ возвращает численные результаты: связные компоненты, состояние замкнутости, доступность корректного расчёта объёма, статистику поверхности относительно заданного направления. Сложные вычисления выполнять вне UI-потока по неизменяемому снимку сетки.

Каждый результат содержит единицы, версию геометрии и ограничения метода. Оценку нависаний для фиксированного направления не выдавать за проверку печатаемости в 5D. Рендер использовать как дополнительный источник.

Сохранение результата

После успешного расчёта плагин сохраняет G-code и 3MF одного состояния, передаёт их backend и получает подтверждение записи в БД. Только после сохранения обоих артефактов запуск получает статус завершённого.

Изменение сцены во время расчёта или экспорта делает результат неактуальным. Ошибка передачи файлов допускает повторную отправку уже рассчитанных артефактов без нового слайсинга.

## 5. Порядок реализации и приёмка

Этап 1 — проверить интеграционные возможности. Получить исходники и дистрибутив нужной версии. Проверить загрузку минимального плагина, встроенное окно, чтение состояния, переключение режимов и доступ к экспортёрам. Установить фактические версии Python/Qt. Этот этап определяет реальные точки интеграции, сохраняя выбранную архитектуру.

Этап 2 — поднять backend и хранение. Добавить PostgreSQL, миграции, репозитории и API диалогов/вложений. Проверить сохранность данных после перезапуска Compose. Обновить устаревшие инструкции шаблона и записать согласованные решения.

Этап 3 — собрать связь с плагином. Реализовать подключение, автоматический контекст, MCP-диспетчер, исполнение одной операции и возврат результата. Проверить работу через настраиваемый адрес, разрыв связи и повторную доставку.

Этап 4 — подключить агента. Реализовать LLM-адаптер, опрос, инструменты, состояния выполнения и оба режима. Сначала проверить протокол локальным тестовым LLM-сервером; тестовый сервер не включать в рабочее поведение продукта.

Этап 5 — замкнуть печать. Довести путь от вложения до сохранённых G-code и 3MF на одной модели в 3D. Затем добавить и проверить 5D, остальные операции, анализ геометрии и продолжение диалога.

Этап 6 — пройти семь заданий. Для каждой модели получить результат через чат, сохранить переписку и собрать каталог результатов. Подготовить устанавливаемый плагин, Compose-конфигурацию и инструкцию запуска.

Обязательные проверки:

- Unit-тесты переходов агента, опроса, остановки после успеха, подтверждений и лимита исправлений.
- Контрактные тесты LLM-адаптера: изображения, несколько tool calls, ошибки, таймауты и некорректные ответы.
- Интеграционные тесты на настоящем PostgreSQL: миграции, транзакции, повторные события, бинарные файлы и восстановление.
- Проверки устаревшей сцены, частично выполненного пакета, отключения плагина и неопределённого исхода команды.
- Проверки сохранения обоих файлов, их контрольных сумм и соответствия одной версии сцены.
- Статическая проверка совместимости плагина с Python 3.5 и проверки исполнения на реальном Qt.
- На выданном STE Slicer: установка, встроенный чат, инструменты, оба режима, 3D/5D, открытие сохранённого 3MF и штатного G-code.
- Backend: Ruff, mypy, unit- и integration-тесты; Compose: миграции, готовность БД и API.

Границы проверки: Windows-стенд пока отсутствует; без него интеграцию с выданным слайсером нельзя считать проверенной. Реальные обращения к платному LLM выполнять только по отдельному ручному запросу. При отсутствии доступа показывать явную ошибку, не подменять агента детерминированным подбором параметров.

Выбранные встроенный UI и агент в Compose отличаются от браузерной SPA и размещения агента в плагине из технического описания сайта. Зафиксировать это как сознательное решение пользователя и расхождение с источником; оригинальное ТЗ не переписывать.

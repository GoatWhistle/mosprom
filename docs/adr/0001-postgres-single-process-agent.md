# Агент работает одним процессом бэкенда, состояние хранится в PostgreSQL

Агент Brim живёт в Compose, а плагин STE Slicer только исполняет инструменты. Состояние запусков,
вызовов, подтверждений и файлов хранится в PostgreSQL 16; выполнение идёт фоновыми задачами одного
процесса без Redis и отдельной очереди.

## Рассмотренные варианты

- **Состояние в памяти процесса:** отклонено — разрыв связи или перезапуск терял бы неопределённый
  исход изменения сцены, а повторная доставка вызова повторяла бы изменение.
- **SQLite:** отклонено — нужны конкурентные записи фоновых задач и обработчиков HTTP и WebSocket.
- **Очередь заданий (Redis) и воркеры:** отклонено — для одного активного запуска на экземпляр
  слайсера это лишний сервис; восстановление даёт сохранённое состояние.
- **Файлы на диске контейнера:** отклонено — постоянное хранение не должно зависеть от файловой
  системы контейнера, поэтому G-code, 3MF и вложения лежат в `bytea` с размером и sha256.

## Следствия

- На один экземпляр слайсера разрешён один активный запуск (частичный уникальный индекс); повторная
  доставка известного `call_id` возвращает сохранённый результат.
- После перезапуска бэкенд возобновляет активные запуски; неопределённый исход вызова не считается
  ни успехом, ни поводом слепо повторить операцию.
- Внешние вызовы (LLM, плагин) выполняются вне открытых транзакций БД.
- Бэкенд масштабируется только вертикально, пока задачи и сигналы живут в одном процессе.
- Ключ LLM хранится только в памяти и после перезапуска передаётся плагином заново.

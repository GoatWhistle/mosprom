# Проектные решения и сбои, от которых они защищают

> Веб-фронтенд удалён 23.10.2026. Упоминания React, nginx и путей `frontend/` ниже
> относятся к прежнему шаблону. В Compose сейчас только backend; встроенный чат STE Slicer
> ещё не реализован.

> Правила, которых нет на других страницах: у каждого — сбой, который оно предотвращает, проверка,
> которая падает при нарушении, и то, чего правило всё ещё не покрывает. Комментариев в коде нет,
> поэтому всё неочевидное в коде объясняется здесь. Правила, описанные на других страницах, здесь не
> повторяются — на них ссылка.

**Читайте, если** вы меняете код и хотите понять, почему он устроен не самым очевидным способом ·

## Как LLM и эмбеддер остаются заменяемыми?

Порты `LanguageModel` и `Embeddings` объявлены в `backend/src/app/usecase/interface.py`, их типы —
в `backend/src/app/domain/inference.py`.

| Правило | Какой сбой предотвращает | Чем закреплено | Остаточный предел |
|---|---|---|---|
| Use case просит у LLM ответ по JSON Schema (`StructuredRequest.schema`), а не свободный текст | Разбор свободного текста ломается при смене модели или промпта | `mypy --strict`; контракт порта | Схема не гарантирует смысл ответа; use case проверяет поля сам |
| `JsonSchema` и `Completion.output` типизированы как `dict[str, Any]` | Схема и ответ произвольны по форме; узкий тип пришлось бы менять на каждый сценарий | Соглашение; `Any` разрешён только здесь | Use case обязан превратить `output` в доменные типы до использования |
| Запрос выбирает класс модели (`Tier`, `Effort`), а не её имя | Имя модели провайдера протекает в use case и привязывает его к поставщику | Адаптер сопоставляет `Tier` с моделью | Разные провайдеры по-разному понимают `Effort` |
| `Embeddings` разделяет `embed_queries` и `embed_documents` | Асимметричные модели (префиксы `query:`/`passage:`) дают худший поиск, если запрос и документ кодируются одинаково | Контракт порта | Симметричная модель реализует оба метода одинаково |
| `Usage` возвращается с каждым ответом | Стоимость и задержка не попадают в замеры | Контракт порта | Не все провайдеры сообщают токены и цену, поэтому поля необязательны |
| Похожесть векторов считает индекс в `repository` (матрица numpy, pgvector), а не `usecase`; `Vector` в порте — `Sequence[float]` | Перебор тысяч векторов циклом Python в `usecase` в разы медленнее и съедает ~8× памяти против `float32` | Соглашение; проверки нет | Перевод numpy ↔ list на границе порта стоит миллисекунды на пакет; если `usecase` сам считает по многим векторам, нужен ADR и тип матрицы N×D |

## Почему Claude подключается через Agent SDK, а вызовы инструментов идут через JSON Schema?

Плагин обращается к backend как к любому OpenAI-совместимому API: `POST /v1/chat/completions`
(`backend/src/app/controller/openai/router.py`). `CompletionService` переводит сообщения OpenAI в
`ChatRequest` и вызывает `ClaudeAgentChatAdapter` из `backend/src/app/adapter/llm/claude_agent.py`.
Claude Agent SDK запускает CLI Claude Code и работает по OAuth-токену подписки
(`claude setup-token`), без платного API-ключа. Токен вводится в поле «Ключ доступа».

| Правило | Какой сбой предотвращает | Чем закреплено | Остаточный предел |
|---|---|---|---|
| `tools=[]`, `setting_sources=[]`, `cwd` — временная пустая папка на каждый вызов | CLI выполняет свои инструменты, читает `CLAUDE.md`, настройки и файлы стенда | `_options`, `test_options_isolate_the_cli_and_pass_the_token` | Глобальные переменные окружения CLI всё равно действуют |
| Токен идёт в `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY` переопределяется пустой строкой | Ключ API из окружения процесса перехватывает авторизацию и тратит деньги | `_options` | Что CLI считает пустую строку отсутствием ключа, живым вызовом не проверено |
| Цикл агента остаётся в плагине (`plugin/Brim/agent/loop.py`): SDK получает всю историю одним сообщением-транскриптом (`<user>`, `<assistant>` с `<tool_call>`, `<tool_result>`), картинки — блоками `image` | SDK сам выполняет инструменты, и подтверждения, журнал вызовов и слайсер обходятся | `claude_transcript.py`, `test_transcript_keeps_images_and_tool_history` | Модель видит прошлые ходы как текст, а не как нативные `tool_use`; качество ниже нативного tool use не измерено |
| При наличии инструментов ответ берётся из `structured_output` по схеме `{text, tool_calls[{name, arguments}]}`, `name` — `enum` имён инструментов; без инструментов — текст `result` | Use case парсит прозу; модель вызывает несуществующий инструмент | `output_schema`, `parse_output`, `test_malformed_structured_output` | Аргументы против схемы инструмента адаптер не проверяет — только что это объект |
| `id` вызова генерирует адаптер (`call_<uuid4>`) | Схема ответа без `id` даёт совпадающие идентификаторы в журнале вызовов | `parse_output` | — |
| Таймаут `LLM_TIMEOUT_SECONDS` через `asyncio.timeout`; ошибки SDK, `is_error`, пустой результат → `ModelTimeout` / `ModelFailure` без текста исключения | Исключение SDK доходит до контроллера как 500 или текст ошибки с токеном попадает в журнал | `test_failures_become_model_failure`, `test_timeout` | Повторов нет; каждый вызов запускает процесс CLI и добавляет задержку |
| `CompletionService` подставляет `MODEL = "opus"` вместо `model` из запроса, в ответ и `/v1/models` — тоже `opus` | Пользователь вписал в плагин `qwen` или устаревший ID, и Claude отвечает ошибкой или слабой моделью | `test_always_uses_opus` | Выбрать `sonnet` или `haiku` через backend нельзя; лимиты подписки на Opus расходуются быстрее |
| Без пакета `claude-agent-sdk` `/v1/chat/completions` отвечает `ModelFailure` (503), подсказка `LLM=true` пишется в журнал | Образ без группы `llm` не стартует | `build_claude_agent` в `main.py`, `UnavailableChatModel` | Импорт внутри функции — исключение из правила «импорты в начале файла» |

Живой вызов 2026-10-23, модель `sonnet`, OAuth-токен подписки, локально (не в контейнере), 3 хода с
8 инструментами из `tools.json`: ход с инструментами — 8,5 с, два параллельных `search_settings`;
ход после результатов — 8,2 с, модель прочитала `<tool_result>` по `id`; текстовый ход без
инструментов — 7,0 с. Цикл агента со слайсером через этот адаптер не прогонялся.

## Как decision-модели (Jev, Laya, OpenJev) остаются заменяемыми?

Decision-модели не пишут текст. Они получают состояние задачи и типизированные вопросы и возвращают
ответ с вероятностями. Порт `DecisionModel` объявлен в `backend/src/app/usecase/interface.py`, его
типы — в `backend/src/app/domain/decision.py`. Адаптер `SystemOneModel` в
`backend/src/app/adapter/decision/system_one.py` работает по контракту `POST /v1/systemone`. Его
повторяют TypeSafe Jev (`https://api.typesafe.ai`), `laya-serve` и decider в OpenJev. Офлайн-замена —
`LexicalDecisionModel` в `backend/src/app/adapter/decision/lexical.py`.

| Правило | Какой сбой предотвращает | Чем закреплено | Остаточный предел |
|---|---|---|---|
| Отдельный порт `DecisionModel`, а не `LanguageModel` с JSON Schema | Вероятности, которые LLM пишет текстом, выглядят как откалиброванные, хотя ими не являются | Контракт порта | LLM-реализации порта нет; режим oneshot из OpenJev сознательно не повторён |
| `noul` из API называется в домене `BinaryQuestion` / `BinaryAnswer.probability` | Жаргон одного вендора протекает в use case | `_question`, `_answer` в `system_one.py` | — |
| `DecisionState` — `str \| Mapping[str, Any]` | API принимает строку или произвольный JSON-объект; узкий тип пришлось бы менять под каждый сценарий | Соглашение; `Any` разрешён только здесь | Use case сам решает, какие поля состояния передать модели |
| В choice не меньше двух вариантов, в score не меньше двух уровней, в запросе хотя бы один вопрос | Вырожденный вопрос уходит провайдеру и возвращается 422 или бессмысленной уверенностью 1.0 | `domain/decision.py`, `tests/unit/domain/test_decision.py` | Лимиты провайдера (255 вариантов, 10 уровней у Jev) не проверяются; Laya заметно теряет точность выше ~20 вариантов |
| Ответ строго сверяется с вопросом: есть по каждому ключу, choice — один из заданных вариантов, probabilities покрывают все варианты или уровни, числа конечны и лежат в [0, 1], score — в [0, число уровней − 1] | Чужой или урезанный ответ сервера тихо превращается в решение | `test_failures_become_decision_failure` | Сумма вероятностей не проверяется; поле `legend` не читается — уровни берутся из запроса |
| Транспортные ошибки, HTTP 4xx/5xx, не-JSON и неверная форма ответа превращаются в `DecisionFailure` (подкласс `ModelFailure`) | Исключение httpx доходит до контроллера как неизвестная 500 | `SystemOneModel.decide` | Повторов нет: 429 и 529 сразу становятся ошибкой, хотя TypeSafe советует экспоненциальный backoff |
| Один `httpx.AsyncClient` на адаптер, закрывается через `aclose()` | Новое TLS-соединение на каждый запрос добавляет задержку сверх 70–500 мс самой модели | `SystemOneModel.__init__`, `aclose`; lifespan в `main.py`, `test_lifespan_exposes_and_closes_providers` | — |
| `Tier` сопоставляется с именем модели (`jev-latest`) в конструкторе; `Usage.model` берётся из ответа (`jev-1.13.0`), если сервер его прислал | Замеры не говорят, какая версия модели отвечала | `DEFAULT_MODELS`, `_usage` | `cost_usd` не заполняется: API не возвращает цену, а тариф вендора может смениться |
| Без `api_key` заголовок `Authorization` не отправляется | Локальный `laya-serve` без `LAYA_API_KEY` получает лишний заголовок | `test_local_server_without_key_or_usage` | С `LAYA_API_KEY` ключ передаётся как к TypeSafe |
| `LexicalDecisionModel` считает пересечение основ слов (первые 5 букв, `ё` → `е`, без стоп-слов) между состоянием и описанием варианта; choice и score — softmax по числу совпадений, binary — сигмоида от `2·совпадения − 1` | Основной сценарий не работает без ключей и скачанных весов | `tests/unit/adapter/decision/test_lexical.py` | Это не модель: синонимы и отрицания не видит, на binary-вопросах почти угадывание. Числа fallback-а не публикуются как качество продукта |

Формат `/v1/systemone` взят из [документации TypeSafe](https://docs.typesafe.ai/api) и
[карточки Laya](https://huggingface.co/ai-ml-space/laya) на 2026-10-14. Совместимость с `laya-serve`
и decider в OpenJev заявлена их авторами, но живым вызовом не проверена: unit-тесты адаптера
используют `httpx.MockTransport`.

## Как бэкенд выбирает реализации при старте?

Точка сборки — `create_app()` в `backend/src/app/main.py`, uvicorn запускает её с `--factory`.
Настройки читает `load_settings` в `backend/src/app/settings.py`.

| Правило | Какой сбой предотвращает | Чем закреплено | Остаточный предел |
|---|---|---|---|
| Окружение читается в `create_app()`, а не при импорте модуля | Тест или скрипт, импортирующий `app.main`, получает настройки чужого окружения | `create_app(settings)`, `tests/unit/composition/test_main.py` | — |
| Без переменных выбираются `lexical` и `none` | Стенд без ключей не стартует или тратит деньги | `test_empty_environment_selects_offline_providers` | Офлайн-реализации `LanguageModel` нет: use case с LLM обязан сам дать запасной путь |
| Неизвестное значение переменной — `ConfigError` с её именем и допустимыми значениями | Опечатка в `.env` молча включает офлайн-режим | `test_invalid_value_names_the_variable` | Ключи провайдеров не проверяются до первого вызова |
| Клиенты создаются в lifespan и закрываются в `finally` | Пул соединений живёт после остановки или создаётся до запуска event loop | `test_lifespan_exposes_and_closes_providers` | Клиенты Claude и Codex создают процесс на каждый вызов и закрытия не требуют |
| `GET /api/v1/health` отвечает `ok`, пока жив процесс, и не опрашивает провайдеров | Платный или медленный провайдер роняет healthcheck и перезапускает контейнер | `controller/health/router.py`, `test_health_reports_liveness` | Это liveness, не готовность: недоступная модель видна только по ошибке сценария |
| Все ошибки — `{code, message}`; `STATUS_BY_ERROR` ищет статус по MRO доменной ошибки; для 5xx уходит общее сообщение класса | Текст ответа провайдера (тело, токены) попадает клиенту; забытая ошибка выглядит как 400 | `controller/errors.py`, `tests/unit/controller/test_errors.py` | Неотображённая `DomainError` — 500 `internal_error` с событием `unmapped_domain_error` в `Logger`: её надо добавить в таблицу |

`LANGUAGE_MODEL=claude` и `codex` в контейнере не проверены: образ не передаёт ключи провайдеров и
не содержит сохранённой авторизации Codex.

## Почему логирование идёт через порт `Logger`?

Порт `Logger` объявлен в `backend/src/app/usecase/interface.py`, реализация на `logging` —
`backend/src/app/adapter/log/stdlib.py`. `create_app()` создаёт один логгер `app`, передаёт его в
`ErrorHandlers` и кладёт в `Providers.logger` для use case.

| Правило | Какой сбой предотвращает | Чем закреплено | Остаточный предел |
|---|---|---|---|
| Use case и контроллеры получают `Logger` через конструктор или аргумент, а не `logging.getLogger` | Слой привязан к stdlib-логгеру: нельзя сменить формат (JSON, OTel) или проверить запись без `caplog` | `test_server_failures_are_logged_through_port` с фейковым логгером; `OWNED_LIBRARIES` в `test_dependency_rule.py` валит импорт `logging` вне `app.adapter.log`, включая `main.py` | Сторонние библиотеки пишут в `logging` сами; правило касается только кода пакета `app` |
| Запись — имя события и поля `LogValue` (`str`, `int`, `float`, `bool`, `None`) | В лог попадает `repr` произвольного объекта с токеном или телом ответа | `mypy --strict` | Строковое поле всё равно может содержать секрет; `domain_failure` пишет `detail` из сообщения ошибки |
| `error(exc=...)` передаёт исключение адаптеру | Трассировка теряется при переходе с `logger.exception` | `test_error_keeps_traceback`, `test_unexpected_error_passes_exception_to_logger` | — |
| 4xx не логируются | Ошибки ввода клиента забивают лог | `test_client_errors_are_not_logged` | — |

## Почему SDK LLM — отдельная группа зависимостей?

`claude-agent-sdk` везёт бинарник CLI Claude Code и раздувает образ бэкенда. Пакет лежит в группе
`llm` в `backend/pyproject.toml`; локально `uv sync` ставит её по умолчанию (`default-groups`), образ —
только при `LLM=true` (`LLM=true docker buildx bake`). Флаг выбирает стадию `deps-${LLM}` в
`backend/Dockerfile`; значения, кроме `true` и `false`, ломают сборку.

Замер 2026-10-14 для прежнего состава группы (Claude и Codex), `docker image ls --tree`, linux/amd64:
без `LLM` образ занимал 155 МБ распакованным, CLI Claude Code — 255 МБ распакованным при колесе
108 МБ. Образ с одной `claude-agent-sdk` 0.2.173 не замерялся.

## Как образ бэкенда кэшируется по слоям?

| Правило | Какой сбой предотвращает | Чем закреплено | Остаточный предел |
|---|---|---|---|
| Базовые образы закреплены тегом и digest (`python:3.12.15-slim@sha256:…`, `uv:0.11.33@sha256:…`) | Новая сборка тянет другой Python или uv, кэш слоёв сбрасывается | `ARG PYTHON_IMAGE`, `ARG UV_IMAGE` | Обновление безопасности базы требует ручной смены digest |
| `uv sync --locked` ставит ровно версии из `uv.lock` | Пакеты обновляются при пересборке без изменения кода | `--locked` падает, если lock расходится с `pyproject.toml` | — |
| Слои: пользователь → базовые зависимости → группа `llm` → `src/` | Правка кода или включение LLM перекачивает и перекладывает все зависимости | Порядок стадий `base`, `deps-true`, финальной; после правки в `src/` bake пересобрал только `COPY src` за 1–4 с (2026-10-14) | Изменение `uv.lock` пересобирает оба слоя зависимостей; первая загрузка группы `llm` при ~120 КБ/с заняла 18 минут |
| `pyproject.toml` и `uv.lock` подключаются bind-mount, кэш uv — cache-mount, uv — mount из своего образа | Колёса скачиваются заново при каждом изменении lock; uv и кэш попадают в образ | `RUN --mount=…` в `backend/Dockerfile` | Cache-mount живёт в BuildKit этой машины; CI без общего кэша качает заново |
| Проект не устанавливается в venv: код лежит в `/srv/src`, путь задаёт `PYTHONPATH` | Правка кода меняет venv и перекладывает слой зависимостей | `ENV PYTHONPATH=/srv/src` | Метаданные пакета `app` в образе недоступны (`importlib.metadata`) |

## Почему тесты бэкенда разделены на unit и integration?

Pre-commit запускает только `backend/tests/unit`, поэтому коммит не ждёт базу и стенд.

## Почему цикл агента живёт в плагине?

Решение — [ADR 0002](adr/0002-plugin-agent-openai-mcp-host.md). Код цикла — `plugin/Brim/agent/`.
Ход выполняется фоновым потоком: системный промпт со свежим контекстом сцены, история чата,
список инструментов со всех MCP-серверов и `ask_user`. Модель отвечает без `tool_calls` — ход
закончен. Лимит — 40 шагов.

Контекст сцены (снимок, настройки, вложения) кладётся в системное сообщение и строится заново на
каждом шаге. Отдельное системное сообщение в середине истории ломает часть OpenAI-совместимых
серверов (vLLM с Qwen требует system только первым), а пользовательское сообщение после результатов
инструментов модель принимает за реплику человека.

`ask_user` не блокирует поток: ход завершается, вопрос виден по последнему вызову `ask_user` без
результата. Ответ пользователя запускает новый ход, который сначала дописывает его результатом
`ask_user`. Поэтому карточка вопроса восстанавливается после переключения чата и перезапуска без
отдельного состояния. Если вместо ответа отправлено новое сообщение, у висящих вызовов появляется
результат `not_answered` / `not_executed`: API требует результат на каждый `tool_call_id`.

Отмена ставит флаг. Пока ход ждёт модель или подтверждение, окно освобождается сразу, а поздний
ответ модели отбрасывается без записи. Во время инструмента отмена передаётся исполнителю
(остановка слайсинга и оставшихся операций), и окно ждёт его завершения.

Картинки (вложения пользователя и `render_scene`) хранятся файлами в папке чата и превращаются в
data URL только при отправке запроса. Изображения из результатов инструментов идут отдельным
пользовательским сообщением после всех результатов шага: роль `tool` в OpenAI API картинки не несёт,
а вставка между результатами нарушила бы порядок.

## Как называются инструменты внешних MCP-серверов?

Инструменты сервера Brim идут без префикса, внешние — `<сервер>__<инструмент>` с заменой символов вне
`[a-zA-Z0-9_-]` на `_` и обрезкой до 64 символов (ограничение имени функции OpenAI). Совпавшее имя
скрывается с предупреждением. Список инструментов запрашивается в начале каждого хода; недоступный
сервер пропускается с предупреждением в окне и не ломает ход. Клиент MCP поддерживает только
Streamable HTTP (JSON и SSE в ответе, `Mcp-Session-Id`, повторная инициализация на 404); stdio-серверы
не поддерживаются, потому что запуск процессов из встроенного Python 3.5 на Windows не проверялся.

## Когда агент спрашивает подтверждение?

`agent/confirmation.py`. Режим «С подтверждением»: каждый `apply_changes` и `slice` сервера Brim и
каждый внешний инструмент без `readOnlyHint`. Режим «Авто»: только рискованные операции —
значение настройки вне `minimum_value..maximum_value`, вне `minimum_value_warning..maximum_value_warning`
или изменение больше чем в 2 раза (настройка `brim/risk_ratio`), а также внешние инструменты с
`destructiveHint`. Границы и текущее значение читаются из стека слайсера на момент вызова.

Отказ возвращается модели результатом `rejected_by_user` с комментарием из поля ввода. Выражения
(`=…`) и нечисловые значения риском не считаются: вычислить их без слайсера нельзя. Локальный MCP для
внешних клиентов подтверждений не спрашивает — доступ к нему защищён токеном и loopback.

## Почему Claude подключается через эмуляцию OpenAI API?

Claude по подписке доступен только через Claude Agent SDK (Python 3.10+, CLI на Node). Backend
принимает `POST /v1/chat/completions`, передаёт Bearer-токен как OAuth-токен Claude и отвечает в
формате OpenAI. Инструменты описываются текстом, ответ — structured output `{text, tool_calls}`.
Каждый шаг — новый запуск CLI с полной расшифровкой (около 8 с в замере 2026-10-23,
`work/session-log.md`), нативный tool use надёжнее. Backend ничего не хранит; токен не логируется.

## Проект на чат в плагине

Каждый чат — папка `chats/<id>/` рядом с кешем плагина: `chat.json` (название, режим, сообщения
OpenAI), `scene.3mf`, `files/` (копии вложений и снимки сцены), `output/` (G-code и 3MF). Индекс
`chats/index.json` хранит активный чат и состояние сцены (`saved` / `empty`). Первое сообщение без
открытого чата создаёт чат и сохраняет в него текущую сцену.

Файл сцены заменяется атомарно: сцена пишется во временный `.part`, проверяется ZIP и модель,
затем `os.replace` подменяет последнюю исправную копию. Пустая сцена хранится как отметка `empty`,
потому что рабочая проверка 3MF требует сетку. Загрузка тоже сначала проверяет архив, поэтому
повреждённый файл не затирает открытую сцену.

Переключение выполняется цепочкой отдельных заданий: заблокировать изменения, сохранить текущий
проект, открыть выбранный, снять блокировку. Блокировка в `SlicerPort` отклоняет `apply_operation`
и `slice`. При ошибке сохранения остаётся текущий проект; при ошибке загрузки возвращается
сохранённая копия предыдущего; если не удалось и это, блокировка остаётся и интерфейс предлагает
восстановить проект. Пока агент работает, переключение предлагает дождаться или остановить ход.

Автосохранение срабатывает через три секунды после последнего изменения сцены и сразу при закрытии
плагина. Черновик и вложения хранятся по чатам в памяти плагина и не переживают перезапуск.
Вложения копируются в папку чата при отправке; символы, недопустимые в именах файлов Windows,
заменяются на `_`.

## Почему лента чата держит все делегаты — 2026-10-23

Делегат ленты создаётся с одной высотой и вырастает после раскладки текста и повторителей: карточка
подтверждения 45 → 182 px, вопрос 66 → 311 px. `ListView` по умолчанию создаёт только видимые
делегаты, а `contentHeight` оценивает по их средней высоте. Выросшие делегаты уходили за край,
уничтожались и создавались снова; `positionViewAtEnd()` из `onContentHeightChanged` замыкал это в
бесконечный цикл. В Qt 5.10 из STE Slicer окно с восстановленной историей зависало: ядро занято
целиком, память больше 1 ГБ. На стенде Qt 5.10 за 5 секунд было 2020 созданий делегатов на 21 запись.

Лента — `Flickable` с `Column` и `Repeater`, без `ListView`: все делегаты создаются сразу, высота
содержимого точная, оценки нет. Пока лента прижата к концу, любое изменение высоты содержимого или
окна прокручивает её вниз; ручная прокрутка вверх снимает прижатие, возврат к концу включает его.

Раньше модель ленты была JS-массивом `view.entries`, и каждое обновление вида (прогресс, автосохранение,
статус) заменяло его целиком: `ListView` пересоздавал все делегаты и сбрасывал `contentY` в 0. Если
пользователь прокрутил историю вверх, новая запись выбрасывала ленту в начало. Теперь `ChatPanel.qml`
сверяет записи с `ListModel` по ключу: совпадающие обновляются на месте (`payload` — JSON записи),
хвост после первого расхождения удаляется и добавляется заново. Смена чата очищает модель и
прокручивает в конец. Харнесс Qt 5.10 (Docker, software-рендер, 40 записей, прокрутка на 1500 px):
до правки новая запись дала `contentY=0`, после — 1500; за прогон 72 создания делегатов на 40 + 1 + 31
записей вместо 112 и стабильный `contentHeight`.

Имя файла в `Content-Disposition` передаётся параметром `filename*` в UTF-8 по RFC 6266 и ASCII-копией
в `filename`. Starlette кодирует заголовки в latin-1, и кириллическое имя вложения давало HTTP 500.

## Почему плагин обходит `call_on_qt_thread` в STE Slicer — 2026-10-23

В Cura `call_on_qt_thread` на главном потоке вызывает функцию сразу. В STE Slicer 7.10.12
(`steslicer/Utils/Threading.pyc`) этой проверки нет: обёртка всегда ставит вызов в очередь Qt и
ждёт его. Обёрнуты `ThreeMFWorkspaceWriter.write`, `GCodeWriter._createSnapshot` (его вызывает
`GCodeWriter.write`) и `ThreeMFWorkspaceReader.read`. Плагин выполняет операции со сценой на
Qt-потоке, поэтому запись 3MF или G-code блокировала слайсер навсегда: поток ждал сам себя.

На время записи `slicer/qt_wrappers.py` подставляет экземпляру писателя исходную функцию из
замыкания обёртки и убирает подмену после вызова. Обёртка с другим именем, например исправная из
Cura с `functools.wraps`, не трогается. Чтение 3MF идёт через задание Uranium в рабочем потоке, ему
обход не нужен.

Имя вложения плагин берёт из `filename*` (UTF-8), а символы, недопустимые в именах файлов Windows,
заменяет на `_`. В ASCII-копии `filename` backend тоже ставит `_`: знак `?` давал `[Errno 22]`.

## Почему все настройки идут в контекст каждого хода — 2026-10-23

`search_settings` возвращает 25 лучших совпадений по словам, а `inspect_profile` обрезал значения
по алфавиту на 400 ключах и терял всё после `retraction_count_max`: `speed_*`, `support_*`, `wall_*`,
`top_*`. В `fdmprinter.def.json` STE-Slicer (ветка `develop`, GitHub) 642 настройки, у многих есть
пары `*_classic` и `*_cylindrical`. Связь пары с родителем непостоянна: `speed_wall_0_cylindrical`
по умолчанию берёт `speed_wall_0`, а `speed_infill_cylindrical` — `speed_print`, мимо `speed_infill`.
Поиск такие ключи пропускает.

Поэтому плагин кладёт в снимок сцены `settings`: включённые (`enabled`) настройки по категориям
строками `key = value unit (type; min..max; options; e0=…, e1=…)`, `*` — переопределение пользователя.
Категории `machine_settings` и `command_line_settings` пропускаются: габариты и сопло уже есть
в `printer`, а G-code-строки длинные. Значения экструдеров пишутся, только если отличаются от
глобальных. Описаний нет, за ними — `search_settings`. Верхняя оценка по определению: 583 строки,
31 тыс. символов; фильтр `enabled` её уменьшает.

Плагин выносит `settings` из JSON сцены в текстовый блок после него. Блок строится заново на каждом
шаге и не сохраняется в истории, поэтому модель не видит устаревших значений. В результаты
инструментов (`read_state`) дамп не входит, иначе каждый `apply_changes` оставлял бы копию в
истории. Около 640 вызовов `getProperty` идут на Qt-потоке, поэтому дамп кешируется. Кеш
сбрасывается сигналами стека (смена стека, профиля, материала, варианта, значений), после каждой
операции и загрузки проекта. Перемещения объектов его не трогают. Время построения на стенде не
измерено.

## Почему чат встроен выдвижной панелью — 2026-10-23

У STE Slicer нет точки расширения для правой панели. Плагин после загрузки главного QML находит элемент `Topbar` по имени QML-типа (`Topbar_QMLTYPE_*`), берёт его
родителя (`contentItem` в `resources/qml/SteSlicer.qml`) и создаёт в нём `DockPanel.qml` под верхней
панелью. Настройки печати слева и чат справа видны одновременно. Цена: опора на внутреннюю раскладку
`SteSlicer.qml`. Если `Topbar` не найден или компонент не создался, меню открывает прежнее окно
`Chat.qml`. В Uranium 3.6 `engineCreatedSignal` испускается после `load()` главного QML, поэтому
панель создаётся из этого сигнала (и повторно пробуется по `mainWindowChanged`), а `objectCreated`
движка к этому моменту уже прошёл.

Панель перекрывает `JobSpecs` в правом нижнем углу, поэтому, пока она открыта, `Binding` сдвигает
его `anchors.rightMargin` на ширину панели; после закрытия Qt возвращает исходный отступ. Мышь и
колесо над панелью не уходят во вьюпорт. Ширина хранится в `brim/panel_width`, по умолчанию 440 px,
не уже 360 px и не шире 70 % окна.

Содержимое чата вынесено в `ChatPanel.qml` (`Item`), `Chat.qml` — окно вокруг него. На Qt 5.10
синхронная загрузка файла, который первым импортирует `QtQuick.Dialogs`, зависает; в слайсере модуль
уже импортирован `SteSlicer.qml`.
## Как окно показывает, что агент работает — 2026-10-23

Ответ LLM приходит целиком, запрос может идти до 300 с. Чтобы долгое ожидание не выглядело как
зависание, над полем ввода стоит строка активности (`ActivityBar.qml`): вращающийся индикатор, фаза
(«Модель думает над ответом», имя выполняемого инструмента, «Слайсинг», «Ждём вашего решения»,
«Останавливаю…»), номер шага модели и секундомер текущей фазы. Фазу и время её начала считает
`chat/activity.py` по событиям цикла; секундомер тикает в QML от `activity.since`, Python для этого
не вызывается. Через 60 с в фазе «думает» строка предлагает подождать или остановить. Если ждём
подтверждения, а окно слайсера не активно, `Window.window.alert(0)` подсвечивает его в панели задач.

Анимация появления привязана к ключу записи: анимируется только запись, которой не было в ленте этого чата. При открытии или
смене чата все записи отмечаются как виденные, и восстановленная история не анимируется. Мигание
карточки подтверждения срабатывает один раз на `call_id`. Длительности и кривые лежат в `Theme.qml`.

## Как выгружается переписка для сдачи — 2026-10-24

Организаторы ждут по каждой модели `results/<модель>/project.3mf`, `result.gcode` и `chat_*.png`.
Кнопка выгрузки в шапке чата спрашивает папку (запоминается в `brim/export_root`) и создаёт в ней
подпапку по имени первой прикреплённой или импортированной модели, иначе по заголовку чата.
В подпапку копируются файлы последнего успешного `slice` этого чата под именами из ТЗ, пишутся
`chat.md` и снимки `chat_NN.png`.

`chat_NN.png` — снимки настоящего интерфейса: `TimelineCapture.qml` прокручивает ленту от начала
шагами в высоту окна минус 48 px перекрытия и снимает всю колонку чата (шапка, лента, поле ввода)
через `grabToImage` в двойном разрешении. Жюри видит тот же экран, что и пользователь. Лента держит
все делегаты (`cacheBuffer`), поэтому высота содержимого известна заранее и прокрутка не догружает
записи. На время съёмки отключено следование за концом ленты, после неё лента возвращается вниз.

`chat.md` дополняет снимки тем, что лента сворачивает: аргументы каждой операции `apply_changes`,
пояснение агента, комментарий к отклонённому вызову, варианты ответов на вопросы. Постраничный
рендер этого текста в PNG (`chat_text_NN.png`) был и убран по решению команды 2026-10-24: в сдачу идут
только снимки интерфейса и Markdown. Старые `chat_*.png` в подпапке удаляются перед выгрузкой; остальные файлы не трогаются.
Если в чате не было слайсинга, выгрузка проходит без `project.3mf` и `result.gcode` и сообщает
об этом.

## Как чат показывает Markdown и принимает файлы — 2026-10-23

В Qt 5.10 слайсера нет `TextEdit.MarkdownText` (появился в 5.14), поэтому `chat/markdown_html.py`
переводит ответ ассистента в подмножество HTML, которое понимает rich text Qt: заголовки, жирный,
курсив, зачёркнутый, код в строке и блоком, списки с вложенностью, таблицы GFM, цитаты, линии,
ссылки и голые URL. Сырой HTML из ответа экранируется. Цвета в разметке — служебные `#c0de01…04`;
`MessageBubble.qml` заменяет их цветами текущей темы, поэтому смена темы не требует пересчёта в Python.
Результат кешируется по тексту (до 512 записей). Сообщения пользователя остаются простым текстом,
выгрузка переписки берёт исходный Markdown. Ссылки открываются во внешнем браузере.

Файлы можно перетащить на панель чата: `DropArea` поверх панели принимает URL, пока агент не занят,
и передаёт каждый в `brim.attach` — те же проверки расширения, размера и числа, что у кнопки.
Над панелью слайсера перетаскивание теперь прикрепляет файл, а не открывает его в сцене.


## Как агент читает документы и выбирает скилл — 2026-10-24

Вложения делятся на три вида: картинка уходит модели сразу как `image_url`, модель и документ —
как путь в контексте. Документ модель читает сама через `read_document`, поэтому большое ТЗ не
раздувает каждый запрос: по умолчанию 20 000 символов за вызов, дальше по `next_start`. Встроенные
в DOCX картинки (до четырёх, до 5 МБ) возвращаются изображениями при первом чтении.

PDF разбирается без библиотек: объекты и потоки объектов, фильтры FlateDecode, ASCII85 и ASCIIHex,
дерево страниц с наследованием ресурсов, Form XObject, шрифты с `ToUnicode` (bfchar и bfrange).
Пробелы и переносы восстанавливаются по положению глифов: ширины берутся из `Widths` или `W`
шрифта. Проверено 2026-10-24 на семи PDF разных генераторов (LaTeX, Chrome, Word, ReportLab)
против `pdftotext` по совпадению слов длиной от 4 букв на первых трёх страницах: доля найденных
слов 0,91–1,00, лишних 0–0,08. PDF кейса организаторов состоит из картинок слайдов, текста в нём
нет; инструмент так и отвечает.

Скилл, закреплённый пользователем, подмешивается в системный промпт как текст инструкции.
Незакреплённые доступны каталогом: имя и описание. Так модель видит все сценарии, но в контексте
лежит одна инструкция. Справочники (`knowledge/*.json`) лежат рядом с кодом и правятся без
изменения логики; ключи настроек в них взяты из Cura 3.6, на стенде их проверяет `unknown_keys`.

Поиск дефекта по тексту сравнивает основы слов: слово короче трёх букв отбрасывается, длиннее
четырёх обрезается на две буквы. Совпадение всей фразы из справочника весит втрое больше частичного,
в ответ попадают не больше трёх дефектов с оценкой не ниже половины лучшей.
